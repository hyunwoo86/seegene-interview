01 의료 자동화 시스템 설계
면접 답변 핵심

“검사별 상태를 등록·진행·완료·배출로 관리하고, 내부적으로는 분주·배양·촬영 단계를 작업 큐로 실행했습니다. 피펫이나 카메라처럼 공유하는 자원은 한 작업만 점유하도록 제어했습니다. 장애 후에는 DB 기록과 실제 장비 상태를 비교해 마지막으로 완료가 확인된 안전 지점부터 재개하고, 명령 ID와 완료 상태로 중복 분주나 촬영을 방지합니다.”

근거: 동시 검사 최대 16개, 명령당 최대 3회 시도, 시도당 60초
02 C#·.NET·WPF
면접 답변 핵심

“장비 통신과 영상 처리는 UI 스레드와 분리하고 async/await로 비동기 실행했습니다. 장시간 작업은 CancellationToken으로 안전하게 중단하며 예외는 로그와 상위 작업 상태에 전달합니다. 화면 변경만 Dispatcher에서 수행하고, 수신 데이터는 생산자-소비자 큐로 처리합니다. MVVM은 화면과 업무 로직 분리, DI와 Adapter는 실제 장비와 Emulator 교체, Repository는 상태 저장소 분리에 활용했습니다.”

03 TCP/IP 장비 통신
면접 답변 핵심

“TCP는 한 번의 수신이 한 메시지라는 보장이 없으므로 길이 정보나 구분자를 기준으로 버퍼에서 완전한 메시지를 조립합니다. 요청 ID로 응답을 연결하고 timeout·heartbeat로 통신 이상을 판단합니다. ACK는 명령 수신 확인일 뿐 실제 동작 완료와 구분합니다. 재연결 후에는 장비 상태를 다시 조회하고, 결과가 불명확한 동작은 자동 재전송보다 안전 정지를 우선합니다.”

04 DB·데이터 무결성
면접 답변 핵심

“검체, 검사, 단계, 장비 명령, 결과, 감사로그를 분리해 저장하고 검사 상태 변경과 명령 이력을 가능한 한 같은 트랜잭션 경계에서 관리합니다. 재실행 시에는 마지막 기록이 아니라 마지막으로 완료가 확인된 안전 지점을 기준으로 복구합니다. 검사 ID와 단계 ID를 중복 실행 방지 키로 사용하고 모든 자동·수동 변경을 audit trail에 남깁니다.”

05 Web Application 보완
면접 답변 핵심

“Web 제품 개발 경험은 없지만 C#/.NET 장비 SW에서 상태관리, 통신, DB, 권한과 오류 복구를 수행했습니다. Web 구조에서는 장비 통신 Worker와 업무 API를 분리하고, REST API로 조회·명령을 처리하며 실시간 상태는 SignalR로 전달하겠습니다. 인증·권한, 중복 요청 방지, 중앙 예외 처리, Swagger와 서버 로그를 기본으로 적용하겠습니다.”

06 SW Validation
면접 답변 핵심

“Verification은 요구사항과 설계대로 만들었는지 확인하는 활동이고, Validation은 실제 사용 목적과 사용자 요구에 맞는지 확인하는 활동입니다. SRS·설계·구현·위험통제·시험을 식별자로 연결하고 정상뿐 아니라 경계·오류·복구 조건을 시험합니다. Emulator는 프로토콜과 흐름의 1차 검증에 사용하고 물리 동작과 성능은 실제 장비에서 확인합니다. 변경 후에는 영향받는 인터페이스와 위험을 기준으로 회귀시험을 선정합니다.”

07 PCR·검사실 자동화
면접 답변 핵심

“PCR 검사는 검체 접수와 바코드 확인, 핵산 추출, 반응액 준비, thermal cycling, 형광 측정과 Ct 분석, 결과 판정 순서로 이해하고 있습니다. 양성·음성·내부 대조군으로 검사 유효성을 확인하고 전처리와 증폭 구역을 분리해 오염을 관리합니다. 검체·시약 lot·장비·사용자·결과 변경 이력을 추적하고 LIS/LIMS에는 승인된 결과만 전달해야 합니다.”

PCR이란? 면접용으로 쉽게 이해하기

PCR은 검체 안에 아주 적게 들어 있는 특정 DNA 구간을 반복해서 복제해, 검출할 수 있을 만큼 늘리는 검사 방법입니다.

쉽게 비유하면

검체 속에서 찾으려는 병원체의 유전자 한 부분을 지정하고, 그 부분만 복사기로 여러 번 복제하는 것과 비슷합니다. 복제가 진행될 때 발생하는 형광 신호를 실시간으로 측정하면 목표 유전자가 있었는지 판단할 수 있습니다.

  3. 장비가 정상이고 필요한 공유 자원이 비어 있는지 확인

private bool _isRunning;

private async void StartButton_Click(
    object sender,
    RoutedEventArgs e)
{
    if (_isRunning)
        return;

    _isRunning = true;
    StartButton.IsEnabled = false;
    StartButton.Content = "검사 중";
    StatusText.Text = "검사를 시작합니다.";

    try
    {
        var progress = new Progress<int>(value =>
        {
            ProgressBar.Value = value;
            StatusText.Text = $"검사 진행률: {value}%";
        });

        var result = await ExecuteInspectionAsync(progress);

        StatusText.Text = result;
    }
    catch (Exception ex)
    {
        StatusText.Text = $"검사 실패: {ex.Message}";
    }
    finally
    {

    }
}
`async void`가 허용되는 곳: 버튼 클릭 같은 이벤트 핸들러. 실제 장비 작업 함수는 `async Task` 또는 `async Task<T>`로 작성해 호출자가 완료와 예외를 기다릴 수 있게 합니다.

3. 실제 장비 작업 함수

private async Task<string> ExecuteInspectionAsync(
    IProgress<int> progress)
{
    progress.Report(10);
    await _device.CheckStatusAsync();

    progress.Report(30);
    await _device.DispenseAsync();

    progress.Report(60);
    await _device.CaptureAsync();

    progress.Report(80);
    await _analyzer.AnalyzeAsync();

    progress.Report(100);
    return "검사가 완료되었습니다.";
}

`Progress<int>`를 UI 스레드에서 생성했기 때문에 백그라운드 작업이 `Report()`를 호출해도 진행률 변경 코드는 UI 스레드에서 실행됩니다.

5. Dispatcher가 필요한 경우

버튼 클릭 함수는 UI 스레드에서 시작하므로 일반적인 `await` 뒤에는 UI 스레드로 돌아옵니다. 하지만 TCP 수신 이벤트처럼 처음부터 백그라운드 스레드에서 호출된 콜백은 Dispatcher를 통해 화면 변경을 전달해야 합니다.

private void OnDeviceMessageReceived(DeviceMessage message)
{
    Application.Current.Dispatcher.InvokeAsync(() =>
    {
        StatusText.Text = message.Status;
        ProgressBar.Value = message.Progress;
    });
}

Windows 앱, 외주 미들웨어, 분석팀처럼 역할을 나눠 설명하고 본인이 직접 담당한 범위를 먼저 답합니다. 정확한 시작·종료 연월과 인원은 확인된 숫자만 말해야 합니다.

9. 요구사항이 모호하거나 서로 충돌하면 어떻게 합니까?

“사용 시나리오와 실패 시 위험을 먼저 확인하고, 정상 흐름과 예외 흐름을 구분합니다. 연구원·HW·RA/QA와 용어와 완료 조건을 맞춘 뒤 요구사항과 인터페이스 문서에 반영합니다. 결정되지 않은 부분은 가정으로 구현하지 않고 이슈로 남겨 승인받습니다.”

10. 외주 개발사의 일정이나 품질이 기대와 다르면?

“감정적으로 압박하기보다 인터페이스 명세와 재현 조건, 기대 결과와 실제 결과를 기준으로 차이를 제시합니다. 전체 일정을 막는 항목과 후속 보완 가능한 항목을 나누고, 중간 산출물과 통합시험 시점을 짧게 설정해 뒤늦게 문제를 발견하지 않도록 하겠습니다.”

③ 시스템 아키텍처·운영·현장 대응 — 7문항

12. 의료 자동화 시스템을 어떤 계층으로 나누겠습니까?

“UI, 업무·검사 Orchestrator, 장비 Adapter, 데이터 저장소, 외부 시스템 연동으로 분리하겠습니다. UI가 장비를 직접 제어하지 않고 Orchestrator가 검사 상태와 자원을 관리하며, Adapter가 장비별 프로토콜 차이를 흡수하도록 하겠습니다.”

13. 한 모듈이 끊겼을 때 전체 검사를 멈춰야 합니까?

“해당 모듈이 안전이나 여러 검체에 공통 영향을 주면 전체를 안전 정지하고, 독립된 검체만 영향받는다면 해당 검사만 보류할 수 있습니다. 판단 기준은 자원 공유 범위, 장비 현재 상태, 결과 무결성과 복구 가능성입니다.”

14. 바코드와 LIS 정보가 일치하지 않으면?

“자동 보정하지 않고 검체를 보류 상태로 전환합니다. 어느 시스템의 값이 기준인지 운영 정책을 따르고, 사용자에게 차이를 명확히 보여 승인된 수정만 허용합니다. 원본 값, 수정자, 시각과 사유를 audit trail에 남깁니다.”

15. 장비·프로토콜·시약 버전 호환은 어떻게 관리합니까?

“장비 firmware, 통신 protocol, SW, 시약 lot와 assay 버전의 호환표를 관리하고 시작 시 조합을 확인합니다. 지원되지 않는 조합은 실행 전에 차단하고, 호환 범위를 변경할 때는 관련 요구사항과 통합시험을 함께 갱신합니다.”

16. 업데이트 중 실패하면 어떻게 복구합니까?

“설치 전 버전·DB schema·여유 공간과 무결성을 확인하고 기존 설정과 DB를 백업합니다. 애플리케이션과 DB migration의 성공을 각각 확인하며, 실패하면 호환 가능한 이전 버전으로 rollback합니다. 재시작 후 장비·DB 상태 확인까지 완료되어야 업데이트 성공으로 판단합니다.”

17. 장애 분석을 위해 어떤 로그를 남깁니까?

“검사 ID·검체 ID·장비·명령 ID를 연결하고 요청, ACK, 실제 완료, 상태 전환과 오류를 같은 시간 기준으로 기록합니다. 사용자 변경과 수동 복구는 audit log로 분리하고, 개인정보와 보안정보는 최소화하거나 보호합니다.”

18. 현장 장애 연락을 받으면 무엇부터 합니까?

“환자·검사 결과와 장비 안전 영향을 먼저 확인하고 추가 검사를 중단할지 판단합니다. 버전, 재현 순서, 로그와 장비 상태를 확보한 뒤 SW·통신·HW·운영 조건으로 가설을 나눕니다. 임시 조치와 근본 수정, 회귀시험과 배포 결과를 구분해 기록합니다.”

20. 카메라를 1대에서 2대로 바꾼 이유와 효과는?

“촬영 영역 두 곳을 한 카메라가 이동하며 처리하던 시간을 줄이기 위한 변경이었습니다. 카메라 ID와 Z축을 구분해 각각의 프레임을 처리했습니다. 정확한 시간 단축률을 측정한 기록은 없어서 ‘2배 빨라졌다’고 말하지 않겠습니다.”

21. 최신 프레임만 남기는 DropOldest가 안전합니까?

“실시간 초점·노출 계산에서 오래된 프레임이 쌓여 현재 위치와 어긋나는 것을 막기 위한 정책입니다. 다만 검사 결과로 저장할 영상은 촬영 명령, 카메라 ID와 완료 시점을 별도로 확인해야 합니다. 두 경로가 같은지 여부는 면접 전 실제 구현 범위를 다시 확인하겠습니다.”

22. 왜 Canny 기반 선명도 값을 사용했습니까?

“여러 선명도 지표를 비교 도구에서 관찰하고 해당 장비·패널 조건에서 초점 부근 변화를 판단하기 좋은 값으로 적용했습니다. Canny가 모든 환경에서 가장 정확하다는 뜻은 아닙니다. 정량 정확도 수치는 없으므로 기준 초점 대비 위치 오차와 반복 편차로 검증하겠다고 답하겠습니다.”
