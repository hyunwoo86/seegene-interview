PCR이란? 면접용으로 쉽게 이해하기

PCR은 검체 안에 아주 적게 들어 있는 특정 DNA 구간을 반복해서 복제해, 검출할 수 있을 만큼 늘리는 검사 방법입니다.

쉽게 비유하면

검체 속에서 찾으려는 병원체의 유전자 한 부분을 지정하고, 그 부분만 복사기로 여러 번 복제하는 것과 비슷합니다. 복제가 진행될 때 발생하는 형광 신호를 실시간으로 측정하면 목표 유전자가 있었는지 판단할 수 있습니다.

먼저 “항생제 감수성 검사 과정을 자동화하는 장비”라고 설명하고, 가운데 앱을 그린 뒤 저장소·장비·영상 분석·시험 도구를 연결한다. 아래 그림은 면접 설명용 개념도이며 실제 클래스 호출 관계, 배선도, DB 스키마를 그대로 옮긴 그림은 아니다.

1. 화이트보드에 그리는 순서

  1. 가운데 앱: 화면(View·ViewModel), 검사 로직, 작업 순서 관리, 장비 연동, 영상 수신·자동 초점을 나눈다. 여러 검사가 로봇·분주기·카메라를 공유하므로 다음 작업에 필요한 장비의 사용 가능 여부와 순서를 관리한다고 설명한다.
  2. 아래 저장소: SQLite, JSON, 영상 폴더, 로그 파일을 따로 그린다. 화면과 저장소를 직접 연결하는 설명보다 앱의 데이터 접근 계층을 통해 조회·저장하는 흐름으로 설명한다.
  3. 오른쪽 장비: 앱 ↔ TCP 명령·응답 ↔ 외주 하드웨어 미들웨어 ↔ 실제 장비 순서로 연결한다. 앱 연동과 하드웨어 구동부의 담당 경계를 구분한다.
  4. 카메라와 분석: 카메라 2대의 영상 수신·버퍼·초점 계산은 앱 쪽에, ImageProc.exe는 별도 분석팀 영역에 그린다. 프로그램 실행과 결과·종료 코드 확인을 화살표로 구분한다.
  5. Emulator: 개발 시 실장비 연동을 대체하는 시험 경로로 점선 연결한다. 명령·응답과 검사 순서는 먼저 확인하되, 실제 충돌·센서 반응·동작 시간은 실장비에서 확인한다고 설명한다.

2. DB와 파일에 무엇을 저장하는가

2. 권장 코드

private bool _isRunning;

private async void StartButton_Click(
    object sender,
    RoutedEventArgs e)
{
    if (_isRunning)
        return;

    _isRunning = true;
    StartButton.IsEnabled = false;
    StartButton.Content = "검사 중";
    StatusText.Text = "검사를 시작합니다.";

    try
    {
        var progress = new Progress<int>(value =>
        {
            ProgressBar.Value = value;
            StatusText.Text = $"검사 진행률: {value}%";
        });

        var result = await ExecuteInspectionAsync(progress);

        StatusText.Text = result;
    }
    catch (Exception ex)
    {
        StatusText.Text = $"검사 실패: {ex.Message}";
    }
    finally
    {
        _isRunning = false;
        StartButton.IsEnabled = true;
        StartButton.Content = "검사 시작";
    }
}
`async void`가 허용되는 곳: 버튼 클릭 같은 이벤트 핸들러. 실제 장비 작업 함수는 `async Task` 또는 `async Task<T>`로 작성해 호출자가 완료와 예외를 기다릴 수 있게 합니다.

3. 실제 장비 작업 함수

private async Task<string> ExecuteInspectionAsync(
    IProgress<int> progress)
{
    progress.Report(10);
    await _device.CheckStatusAsync();

    progress.Report(30);
    await _device.DispenseAsync();

    progress.Report(60);
    await _device.CaptureAsync();

    progress.Report(80);
    await _analyzer.AnalyzeAsync();

    progress.Report(100);
    return "검사가 완료되었습니다.";
}

`Progress<int>`를 UI 스레드에서 생성했기 때문에 백그라운드 작업이 `Report()`를 호출해도 진행률 변경 코드는 UI 스레드에서 실행됩니다.

5. Dispatcher가 필요한 경우

버튼 클릭 함수는 UI 스레드에서 시작하므로 일반적인 `await` 뒤에는 UI 스레드로 돌아옵니다. 하지만 TCP 수신 이벤트처럼 처음부터 백그라운드 스레드에서 호출된 콜백은 Dispatcher를 통해 화면 변경을 전달해야 합니다.

private void OnDeviceMessageReceived(DeviceMessage message)
{
    Application.Current.Dispatcher.InvokeAsync(() =>
    {
        StatusText.Text = message.Status;
        ProgressBar.Value = message.Progress;
    });
}

6. 면접 답변

“버튼 클릭 이벤트에서는 중복 실행을 막고 버튼과 진행 상태를 관리한 뒤, 실제 장비 동작은 `Task`를 반환하는 비동기 함수로 분리했습니다. TCP 통신과 장비 완료 대기 중에는 UI 스레드를 점유하지 않도록 `await`를 사용했습니다. 작업 결과는 `Progress<T>`로 전달했고, TCP 수신 콜백처럼 백그라운드 스레드에서 직접 들어오는 화면 변경만 Dispatcher를 통해 UI 스레드에 전달했습니다. 오류가 발생해도 `finally`에서 버튼 상태가 복구되도록 구성했습니다.”

이직 사유 답변

여러 번 옮긴 이력을 “역량을 넓히고 본업으로 돌아오는 흐름”으로 보이게 합니다.

숫자는 13년·7년 반 두 개만. 사이버보안은 두 번째 강점으로 짧게.

라운드 2 · dRAST 경험 검증 (약 15분)

4. dRAST에서 본인이 직접 한 범위는?

“제가 직접 담당한 것은 Windows 애플리케이션의 UI, 검사 흐름과 작업 순서, TCP 명령·응답 연동, 검사 상태 저장·복구, Emulator와 통합시험 도구입니다. 하드웨어 미들웨어는 외주 개발사가, 영상분석 알고리즘은 분석팀이 맡았습니다. 저는 두 시스템과의 인터페이스와 오류 조건을 협의해서 전체 검사 흐름 안에 통합하는 책임을 졌습니다.”
꼬리 “PM이셨나요?” → “공식 PM은 아니었고 직접 개발하는 테크리드에 가까웠습니다. 예산이나 인사 권한은 없었습니다.”

[확인] dRAST 3.0 참여 기간, 앱 개발 인원, 대표 클래스·화면·DB 테이블 각 1개

5. 검사 도중 프로그램이 죽으면?

“저장된 상태만 믿고 다음 단계로 가지 않았습니다. JSON과 SQLite에 저장된 검사 상태를 읽고, 장비의 실제 상태와 비교해서 완료가 확인된 마지막 안전 지점부터 재개했습니다. 분주처럼 되돌릴 수 없고 실행 여부가 불명확한 단계는 자동으로 다시 실행하지 않고, 보류한 뒤 사용자가 확인하게 했습니다.”
꼬리 “DB엔 미완료인데 분주는 끝났다면?” → “자동으로 다시 분주하지 않습니다. 근거를 모아 보여주고 운영자가 보류·폐기·수동 복구 중에서 승인하도록 합니다.”

[확인] JSON과 SQLite의 실제 역할 분담, 자동 재개 가능·불가능 단계

6. 장비 응답이 늦을 때 TCP는?

“소켓 연결 상태와 장비 작업 상태를 따로 봤습니다. 명령마다 timeout을 두었고 dRAST에서는 명령당 최대 3회, 시도당 60초였습니다. ACK는 명령을 받았다는 뜻이지 동작이 끝났다는 뜻이 아니라서, timeout이 나면 바로 재전송하지 않고 장비 상태를 먼저 조회했습니다.”

[확인] 3회·60초를 직접 정했는지, HW팀과 협의한 명세였는지

7. 16개 검사를 어떻게 스케줄링했나요?

“16개가 물리적으로 동시에 움직인다는 뜻은 아닙니다. 검사 16개의 상태와 작업을 동시에 관리하고, 피펫이나 카메라 같은 공유 자원은 한 번에 한 작업만 점유하게 했습니다. 스케줄러가 선행 단계 완료, 장비 상태, 자원 여유를 확인한 뒤에만 명령을 보냈습니다.”
꼬리 “처리량은 얼마나 좋아졌나요?” → “전후 측정 자료가 없어 수치로 말씀드리긴 어렵습니다. 대신 구조를 설명드리겠습니다.”

라운드 3 · 공백 영역 (약 15분)

8. Web 경험이 자격요건인데요?

9. PCR은 아십니까?

“실무 경험은 없습니다. PCR은 검체에서 추출한 특정 유전자 구간을 반복 증폭해 병원체가 있는지 확인하는 검사이고, Real-time PCR은 증폭 중 형광을 매 cycle 측정해 Ct 값으로 판정합니다. 자동화 SW 관점에서는 검체·시약 식별, 분주, 온도 cycle, 대조군, 오염 방지, 결과 추적성이 중요하다고 봅니다.”
꼬리 “dRAST 경험이 도움이 되나요?” → “자동화 구조는 그대로 연결되지만, 증폭·대조군 판정·오염 방지 규칙은 PCR 고유의 것이라 임의로 단순화하지 않고 배우겠습니다.”

10. Verification과 Validation의 차이는?

“‘통신이 끊기면 검사를 보류한다’는 요구사항대로 코드와 시험 결과가 나오는지 확인하는 게 Verification이고, 실제 사용자가 장애 후 검체를 혼동하지 않고 안전하게 복구할 수 있는지 사용 시나리오로 확인하는 게 Validation입니다. dRAST에서는 Test ID에 SRS·SDDS 식별자를 연결했고, 레이와트에서는 SRS·SDS·위험통제와 시험 결과를 연결하는 IEC 62304 V&V 문서를 보완하고 있습니다.”

[확인] 실제 SRS ID 하나로 설계·위험통제·시험 결과까지 이어서 말하기

11. (화이트보드) 검체 100개, 한 모듈이 끊겨도 유실·중복 없이 재개하려면?

“먼저 처리량, 실패 조건, 안전 상태, 사람이 개입할 기준을 확인하겠습니다. 구조는 모듈, Orchestrator, DB, UI, LIS로 나누고, 검체마다 상태기계를 둡니다. 명령마다 ID를 붙이고 보내기 전과 응답 후 상태를 저장합니다. 모듈이 끊기면 그 모듈의 검체만 보류하고, 재연결 후 장비 상태를 재조회해 완료·미실행·불명확으로 나눕니다. 불명확한 비가역 단계는 자동 재시도하지 않습니다. 모든 변경은 audit log에 남기고, Emulator 오류 주입과 실장비 통합시험으로 검증하겠습니다.”

01 “dRAST를 본인이 만들었다는 근거가 무엇입니까?”
  1. 본인이 직접 작성한 모듈과 다른 팀이 만든 모듈을 정확히 나눠보세요.제가 직접 담당한 범위는 Windows 애플리케이션의 UI, 검사 흐름과 작업 순서, TCP 명령·응답 연동, 상태 저장·복구, Emulator 및 통합시험 도구입니다. 장비 구동 미들웨어는 외주 개발사, 영상분석 알고리즘은 분석팀이 담당했고 저는 인터페이스와 오류 처리 조건을 협의해 통합했습니다.
  2. 가장 어려웠던 클래스나 흐름 하나를 화이트보드에 그려보세요.검체별 상태를 관리하는 검사 흐름을 중심에 두고, 작업 큐·장비 Adapter·SQLite·UI를 연결해 그리겠습니다. 정상 흐름뿐 아니라 명령 전송, ACK, 실제 완료, 상태 저장, 실패 시 보류·재개의 순서까지 표시하겠습니다. 실제 클래스명은 면접 전 코드 기준으로 다시 확인하겠습니다.
  3. 본인이 빠졌다면 프로젝트에서 실제로 무엇이 멈췄습니까?Windows 앱의 검사 흐름 변경, 미들웨어·분석 프로그램 연동 이슈의 원인 분리, Emulator 기반 사전 검증과 배포 대응이 지연됐을 가능성이 큽니다. 다만 프로젝트가 저 한 명에게만 의존했다고 과장하지 않고, 제 담당 영역의 공백이 무엇이었는지로 설명하겠습니다.
  4. 코드리뷰·시험·배포 중 최종 결정권은 누구에게 있었습니까?제가 구현과 기술 검토, 통합시험 준비를 주도한 부분은 있지만 조직의 최종 승인권자까지 저였다고 말하지 않겠습니다. 코드와 시험 결과를 담당자·리더와 검토하고 정해진 승인 절차에 따라 배포했습니다. 당시 정확한 승인 체계와 제 권한 범위는 면접 전 확인하겠습니다.

02 “‘제품화를 리드했다’는 표현이 과장 아닌가요?”
  1. 공식 직책이 PM이나 PL이었습니까?공식 PM·PL 직책이었다고 말하지 않겠습니다. 직접 개발하면서 앱의 기술 방향과 통합 이슈를 조율한 테크리드 성격의 역할이었습니다.
  2. 일정·예산·인사 중 무엇을 실제로 결정했습니까?예산과 인사 결정권은 없었습니다. 제가 관여한 것은 담당 기능의 구현 순서, 기술적 우선순위, 인터페이스 협의, 통합시험 일정과 이슈 대응이었습니다. 제품 전체 일정의 최종 승인은 조직 책임자의 영역이었습니다.
  3. 누구에게 업무를 배정했고, 지연을 어떻게 관리했습니까?정식 인사 권한으로 업무를 배정했다기보다 기능 담당자들과 인터페이스별 할 일을 나누고, 전체 흐름을 막는 이슈를 우선 추적했습니다. 재현 조건·담당·목표일·통합시험 시점을 명확히 해 지연을 조기에 드러내는 방식으로 관리했습니다.
  4. 결국 개발자였던 것 아닌가요?맞습니다. 제 기반 역할은 개발자였습니다. 다만 제 코드만 작성한 것이 아니라 앱과 장비·분석 프로그램 사이의 경계를 정의하고 통합검증과 배포까지 책임졌다는 점이 일반적인 개별 기능 개발보다 넓었던 부분입니다.
안전한 답변“공식 PM이라고 표현하지 않겠습니다. 직접 개발하는 테크리드에 가까웠습니다. 앱 설계·구현과 시스템 연동, 통합검증, 배포·유지보수를 맡고 기능별 이슈와 협업 일정을 조율했습니다. 회사 전체 예산이나 인사 권한까지 맡은 것은 아닙니다.”

03 “프로그램이 죽었을 때 정말 안전하게 재개됐습니까?”
  1. 프로세스가 명령 전송 직후 죽으면 완료 여부를 어떻게 압니까?재시작 후 저장값만 보고 재전송하지 않고 장비의 현재 상태나 완료 이력을 조회해야 합니다. 조회로도 확인할 수 없다면 결과가 모호한 상태로 분류하고 자동 진행을 중단합니다. 당시 장비가 제공한 상태 조회 범위는 실제 명세 기준으로 답하겠습니다.
  2. DB에는 미완료인데 실제 분주는 끝난 경우는요?분주는 되돌릴 수 없고 중복 실행 위험이 있으므로 자동으로 다시 분주하지 않습니다. 장비 이력, 잔량, 다음 단계 상태 등 확인 가능한 근거를 모으고 운영자가 검체를 보류·폐기·수동 복구하도록 승인 흐름을 둡니다.
  3. JSON과 SQLite가 서로 다르면 무엇을 신뢰합니까?두 저장소의 목적과 갱신 시점이 먼저 정의되어야 합니다. 권위 저장소를 하나로 정하고 다른 쪽은 캐시나 보조 복구 정보로 사용해야 합니다. dRAST 당시 실제 역할과 우선순위는 확인해 사실대로 말하고, 기억이 불확실하면 설계 원칙과 실제 구현을 섞지 않겠습니다.
  4. 자동 재개할 수 없는 단계와 그 이유는 무엇입니까?분주처럼 실행 여부가 불명확하면 중복 시 검체·결과에 영향을 주는 비가역 단계는 자동 재개 대상에서 제외합니다. 반면 상태 조회가 가능하고 동일 요청의 중복 효과가 없는 조회·화면 갱신 등은 상대적으로 안전하게 재실행할 수 있습니다.
  5. 그 복구 로직을 어떻게 시험했습니까?Emulator에서 정상·timeout·오류 응답을 만들고 단계별로 프로그램 종료나 통신 단절을 발생시켜 상태 전환과 재개 지점을 확인합니다. 이후 실제 장비에서 가능한 오류를 제한적으로 주입해 물리 상태와 기록이 일치하는지 검증해야 합니다. 제가 실제 수행한 시험 항목은 기록 기준으로 확정하겠습니다.
안전한 답변“저장 상태만 믿고 다음 단계로 가지 않습니다. 장비의 실제 상태와 완료 응답을 대조하고 마지막으로 완료가 확인된 안전 지점을 정합니다. 결과가 모호하고 되돌릴 수 없는 분주 동작은 자동 재전송하지 않고 보류·안전정지 후 사용자가 확인하도록 합니다. JSON·SQLite의 실제 역할과 우선순위는 당시 구현 기준으로 구분해 답하겠습니다.”
면접 전 확정저장 시점, 실제 저장 필드, 두 저장소의 역할, 재개 가능·불가능 단계, 오류 주입 시험 사례
04 “TCP 재시도 3회·60초는 왜 그렇게 정했습니까?”
  1. 근거 없이 임의로 정한 숫자 아닌가요?당시 장비의 정상 처리시간과 운영상 허용 가능한 대기시간을 기준으로 정한 정책입니다. 다만 제가 단독으로 산출한 값인지 협의된 명세인지 정확히 구분해 답하겠습니다. 새 시스템이라면 측정된 처리시간 분포와 안전 영향으로 timeout을 결정하겠습니다.
  2. ACK가 유실되고 장비 동작은 끝났다면 재시도해도 됩니까?바로 재시도하면 안 됩니다. ACK는 수신 확인일 뿐 실제 동작 완료와 다를 수 있으므로 장비 상태나 명령 이력을 먼저 조회해야 합니다. 완료 여부를 확인할 수 없는 비가역 명령이면 안전정지와 사용자 확인을 선택합니다.
  3. 소켓 연결 상태와 장비 정상 상태를 어떻게 구분합니까?TCP 연결 유지 여부, heartbeat 응답, 개별 명령의 ACK, 실제 작업 완료 상태를 별도 층으로 관리합니다. 소켓이 연결돼 있어도 장비가 busy나 fault일 수 있으므로 상태 조회와 명령별 timeout을 함께 봅니다.
  4. 패킷 분할·병합과 순서 뒤바뀜은 어떻게 처리했습니까?TCP는 메시지 경계를 보장하지 않으므로 수신 버퍼에서 길이 필드나 구분자 기준으로 완전한 프레임을 조립합니다. 요청 ID나 순번으로 응답을 연결하고 예상하지 않은 응답은 로그를 남긴 뒤 상태를 재확인합니다. 실제 프로토콜의 framing 방식은 명세 기준으로 답하겠습니다.
  5. 재연결 뒤 진행 중 명령은 어떻게 정합성을 맞춥니까?마지막 로컬 기록과 장비의 현재 상태·완료 이력을 비교해 진행 중 명령을 완료, 실패, 불명확으로 분류합니다. 완료면 다음 단계로, 실패면 정책에 따른 재시도나 보류로 가며, 불명확하면 자동 재전송하지 않습니다.
안전한 답변“3회·60초는 당시 장비의 정상 처리시간과 운영 허용시간을 바탕으로 적용한 정책이지만, 모든 명령을 무조건 재전송한 것은 아닙니다. ACK와 실제 완료를 분리하고, 타임아웃 뒤에는 장비 상태를 먼저 조회합니다. 완료 여부가 불명확한 비가역 동작은 자동 재시도보다 안전정지를 우선합니다.”
추가 준비framing 규칙, 요청 ID 유무, heartbeat 주기, timeout 값의 실제 결정 주체를 확인
05 “16개 동시 검사를 실제로 어떻게 스케줄링했습니까?”
  1. 동시 16개라는 것이 물리적 동시 실행입니까, 등록 가능한 수입니까?16개가 모든 동작을 물리적으로 동시에 수행한다는 뜻은 아닙니다. 여러 검사 슬롯의 상태와 작업을 동시에 관리하되 피펫·카메라 같은 공유 자원은 순차 점유합니다. 16개의 정확한 제품상 의미는 매뉴얼과 구현을 확인해 표현하겠습니다.
  2. 피펫·카메라·배양 위치 충돌을 누가 막습니까?검사 Orchestrator나 작업 스케줄러가 자원별 점유 상태와 interlock을 확인한 뒤 명령을 내립니다. 장비 미들웨어의 물리 안전 interlock과 앱의 논리적 순서 제어가 각각 어디까지 담당했는지는 구분해 설명하겠습니다.
  3. 우선순위가 높은 검체 때문에 낮은 검체가 굶지 않습니까?긴급도만 계속 우선하면 starvation이 생길 수 있으므로 시간 제한이 있는 단계, 대기시간과 우선순위를 함께 고려해야 합니다. 당시 제품에서는 코드상 정의된 우선순위와 실제 운영에 사용한 우선순위가 달랐으므로 실제 적용 범위만 말하겠습니다.
  4. 중간 검체를 취소하면 예약된 자원은 어떻게 해제합니까?즉시 취소가 안전한지 현재 동작부터 확인합니다. 진행 중인 물리 동작은 안전 지점까지 종료하거나 장비의 안전 중단 절차를 따르고, 이후 대기 작업과 예약 자원을 해제하며 검체 상태와 취소 사유를 기록합니다.
  5. 처리량이나 평균 검사시간이 실제로 얼마나 개선됐습니까?측정 자료가 확인된 수치만 답하겠습니다. 자료가 없다면 동시 관리 범위와 병목을 줄인 설계는 설명하되, ‘몇 퍼센트 개선’이나 ‘두 배 향상’처럼 검증되지 않은 성과는 말하지 않겠습니다.
안전한 답변“16개는 검사 슬롯과 작업 흐름을 동시에 관리한 최대 범위로 설명하겠습니다. 각 검체는 단계별 작업 큐를 갖고 공유 자원은 한 작업만 점유하도록 했습니다. 우선순위는 실제 운영에 사용한 범위와 코드상 정의를 구분하겠습니다. 처리량 개선 수치는 측정 자료가 없으면 추정해서 말하지 않겠습니다.”

06 “Web 실무 경험이 없는데 왜 뽑아야 합니까?”
  1. WPF와 Web은 다른데 무엇이 전환 가능하다는 말입니까?UI 렌더링과 배포 방식은 다르지만 장비 상태기계, 통신 Adapter, DB 무결성, 권한과 오류 복구 같은 도메인 로직은 이전 가능합니다. 반면 HTTP 요청 생명주기, 동시 사용자, 인증 토큰, 서버 배포와 관측성은 새로 익혀야 할 영역이라고 구분하겠습니다.
  2. HTTP는 상태가 없는데 장비의 긴 작업을 어떻게 관리합니까?명령 요청에 작업 ID를 발급하고 즉시 접수 상태를 반환합니다. Worker가 장비 작업을 수행하면서 상태를 영속화하고, 클라이언트는 API 조회나 SignalR 알림으로 진행 상황을 받습니다. 브라우저 연결이 끊겨도 작업 상태는 서버에 남아야 합니다.
  3. 서버가 여러 대면 장비 연결의 소유권은 누가 가집니까?일반 Web 인스턴스가 각각 장비에 연결하면 중복 명령 위험이 있습니다. 장비 연결을 전담하는 단일 Worker나 장비별 리더를 두고, 명령 큐와 분산 잠금·lease로 소유권을 명확히 하겠습니다. 구체적 방식은 가용성 요구와 배포 환경에 따라 선택합니다.
  4. SignalR 연결이 끊기면 화면 상태가 유실되지 않습니까?SignalR을 권위 저장소로 사용하지 않습니다. 상태 변경은 먼저 서버 DB에 저장하고 SignalR은 알림만 담당합니다. 재접속한 화면은 마지막 이벤트에 의존하지 않고 API로 현재 상태와 필요한 이력을 다시 조회합니다.
  5. 말뿐 아니라 직접 만들어본 결과물이 있습니까?제품 Web 실무 경험은 없다고 명확히 답하겠습니다. 면접 전 PoC를 완성했다면 실행 화면과 구조를 보여주고, 아직 완성하지 못했다면 학습 중인 범위까지만 말하겠습니다. 만들지 않은 결과물을 경험처럼 표현하지 않겠습니다.
안전한 답변“Web 제품 실무 경험이 없는 것은 사실입니다. 장비 연결을 담당하는 단일 Worker와 업무 API를 분리하고, 장시간 명령은 작업 ID와 영속 상태로 관리하겠습니다. SignalR은 알림 채널로 사용하고 재접속 시 DB에서 최신 상태를 조회합니다. WPF와 같다고 주장하지 않고 ASP.NET Core의 요청 생명주기, 인증·권한, 배포·관측성을 별도로 보완하겠습니다.”

  3. 변경 영향분석 때문에 추가된 회귀시험 사례가 있습니까?통신이나 상태복구 변경이라면 수정한 함수 시험뿐 아니라 timeout, 재연결, 중복 명령 방지, DB 복구와 전체 검사 흐름을 영향 범위로 봅니다. 실제로 추가했던 시험 사례는 변경 내용·추가 이유·결과를 산출물 기준으로 하나 준비하겠습니다.
  4. 시험이 실패했는데 출시 일정 때문에 넘어간 적은 없습니까?실패를 숨기거나 합격으로 바꾸면 안 됩니다. 결함의 안전·성능 영향과 발생 조건을 평가하고 수정·재시험하거나, 허용 가능한 잔여 위험이라면 정식 승인과 근거를 남겨야 합니다. 제 실제 경험에서는 어떤 결정과 승인 절차를 거쳤는지 사실대로 답하겠습니다.

08 “PCR을 잘 모르는데 IVD 경험이 정말 도움이 됩니까?”
  1. PCR의 변성·결합·신장 단계를 설명해보세요.변성은 이중가닥 DNA를 열로 분리하고, 결합은 온도를 낮춰 primer가 표적 서열에 붙게 하며, 신장은 DNA polymerase가 primer부터 새 가닥을 합성하는 단계입니다. 이 cycle을 반복해 표적 DNA를 검출 가능한 수준으로 증폭합니다.
  2. Ct가 낮다는 것은 무엇을 의미합니까?형광 신호가 기준선을 넘는 cycle이 이르다는 뜻이므로 일반적으로 시작 표적량이 더 많았을 가능성을 의미합니다. 다만 Ct 하나만으로 감염이나 정량 결과를 단정하지 않고 assay 기준, 대조군, 검체 품질과 함께 판정해야 합니다.
  3. 양성·음성·내부 대조군 중 하나가 실패하면 어떻게 합니까?어떤 대조군이 실패했는지에 따라 오염, 시약·증폭 실패, 추출 실패나 억제 가능성을 판단합니다. 유효성 규칙을 충족하지 못한 run이나 검체 결과는 자동 보고하지 않고 무효·재검 대상으로 처리하며 원인과 조치를 기록합니다.
  4. Carry-over contamination을 SW가 어떻게 줄입니까?SW만으로 제거할 수는 없지만 전처리·증폭 구역과 작업 순서를 강제하고, consumable 재사용 방지, 바코드·lot 추적, 세척·교체 절차 확인, 오염 의심 시 결과 보류와 경고로 통제할 수 있습니다. 물리적 구역 분리와 작업 절차가 함께 필요합니다.
  5. dRAST와 PCR의 가장 위험한 차이는 무엇입니까?공통 자동화 구조만 보고 PCR 고유의 증폭·오염·대조군 규칙을 단순화하는 것이 가장 위험하다고 생각합니다. dRAST 경험은 상태·장비·추적성에 활용하되 assay 판정과 contamination control은 도메인 전문가와 요구사항을 확인해야 합니다.
안전한 답변“PCR 직접 실무 경험은 없습니다. 다만 검체 식별, 분주, 장비 상태, 단계별 추적성, 오류 복구와 결과 승인이라는 자동화 구조는 연결됩니다. PCR 고유의 thermal cycling, 형광·Ct 판정, 대조군 유효성, 구역 분리와 오염방지 규칙은 새로 학습해야 합니다. 모르는 도메인 규칙을 기존 경험으로 임의 대체하지 않겠습니다.”

09 “사이버보안이 실제 장비 안전과 무슨 관계입니까?”
  1. RBAC가 있어도 관리자 계정이 탈취되면 어떻게 합니까?RBAC만으로 충분하지 않습니다. 강한 인증과 계정 잠금·세션 정책, 관리자 기능의 재인증, 중요 변경 감사로그와 이상행위 모니터링, 최소권한과 계정 분리를 함께 적용합니다. 위험도가 높은 설정 변경에는 이중 확인이나 승인도 고려합니다.
  2. TLS를 적용하면 장비 내부 통신은 모두 안전합니까?아닙니다. TLS는 전송 중 기밀성과 무결성을 돕지만 endpoint 자체의 취약점, 인증서 관리, 권한 오용, 재전송 공격과 가용성 문제까지 해결하지 않습니다. 상호 인증, 메시지 식별자, 네트워크 분리, 입력 검증과 감사로그가 함께 필요합니다.
  3. SBOM에 Critical CVE가 나오면 바로 업데이트합니까?CVSS 점수만으로 결정하지 않습니다. 해당 컴포넌트 버전, 취약 기능 사용 여부, 공격 경로와 제품 환경을 평가해 실제 악용 가능성과 환자 영향을 판단합니다. 긴급 완화가 필요하면 네트워크 차단 등 임시 통제를 적용하고 검증된 패치를 배포합니다.
  4. 보안 패치 때문에 검사 기능이 깨지는 위험은요?그래서 패치도 일반 기능 변경처럼 영향분석과 회귀시험이 필요합니다. 통신, 드라이버, DB, 성능과 핵심 검사 흐름을 시험하고 rollback 계획을 준비한 뒤 단계적으로 배포합니다.
  5. 가용성과 보안이 충돌하면 무엇을 우선합니까?일률적으로 하나를 우선하지 않고 환자와 검사 결과에 미치는 위험을 비교합니다. 즉시 차단이 더 위험하다면 노출을 제한한 임시 통제 아래 운영할 수 있지만, 결정·근거·기간을 승인받고 영구 조치 일정을 관리해야 합니다.
안전한 답변“보안 기능의 목적은 검사 가용성, 결과 무결성과 환자 안전을 지키는 것입니다. RBAC만이 아니라 계정 정책·감사로그·무결성 검증·네트워크 경계를 함께 봅니다. CVE는 점수만으로 즉시 패치하지 않고 제품 노출과 악용 가능성을 평가해 VEX와 위험평가에 남기며, 패치는 영향분석과 회귀시험 후 배포합니다.”

10 “외주사·HW팀과 충돌했을 때 실제로 무엇을 했습니까?”
  1. 상대 팀이 자기 문제 아니라고 하면 어떻게 설득했습니까?말로 책임을 주장하기보다 같은 재현 절차에서 앱 로그, TCP 기록, 미들웨어 로그와 장비 상태를 시간순으로 맞춥니다. 어느 경계까지 정상이고 어디서 기대와 달라지는지 함께 확인해 다음 시험의 담당과 합격 조건을 합의합니다.
  2. 명세 자체가 모호했던 책임은 누구에게 있었습니까?공동 책임일 수 있고 제 책임도 피하지 않겠습니다. 제가 인터페이스 통합을 맡았다면 timeout, 오류코드, ACK와 완료의 의미를 더 일찍 명확히 했어야 합니다. 모호한 부분을 발견한 뒤 문서와 시험 조건에 반영한 과정까지 설명하겠습니다.
  3. 일정이 밀렸을 때 기능을 줄이거나 출시를 늦춘 적이 있습니까?안전과 결과 무결성에 영향을 주는 기능은 일정 때문에 생략할 수 없습니다. 필수·후속 가능 항목을 위험 기준으로 나누고, 필수 기능이 검증되지 않았다면 지연 필요성을 근거와 함께 보고합니다. 실제 의사결정 사례와 최종 승인자는 사실대로 구분하겠습니다.
  4. 감정적으로 충돌한 경험과 본인의 잘못은 없었습니까?처음에는 각 팀이 자기 로그만 보고 판단해 대화가 평행선을 달린 적이 있습니다. 저도 기술 설명을 상대 팀의 관점과 재현 조건으로 충분히 정리하지 못한 부분이 있었습니다. 이후 공통 시간축과 기대·실제 결과 표로 논점을 바꿔 해결했습니다.
  5. 재발 방지를 위해 문서나 프로세스를 무엇을 바꿨습니까?명령별 입력, ACK, 완료 조건, timeout, 오류코드와 재시도 가능 여부를 인터페이스 문서에 명시하고 양쪽이 같은 시나리오로 시험하도록 했습니다. 변경 시 통합시험 항목도 함께 갱신해 구두 합의로 끝나지 않게 했습니다.
안전한 답변“누구 책임인지부터 논쟁하기보다 앱 로그, TCP 기록, 미들웨어 로그와 장비 상태를 같은 시간축으로 맞췄습니다. 재현 조건과 기대·실제 결과를 합의하고 다음 시험에서 확인할 항목을 나눴습니다. 제 설명이나 명세가 부족했던 부분도 인정하고 인터페이스의 timeout·오류코드·완료 조건을 문서에 보완했습니다.”

1. 프로세스·스레드·비동기·UI

1. 멀티프로세스와 멀티스레드의 차이는?

“멀티프로세스는 독립된 실행 단위를 여러 개 사용하고, 멀티스레드는 한 프로세스 안에서 여러 실행 흐름을 사용합니다. 프로세스는 기본적으로 주소 공간이 분리되어 소켓·파이프 등의 IPC가 필요합니다. 스레드는 메모리를 공유하므로 데이터 전달은 편하지만 동시 접근을 제어해야 합니다. 프로세스 분리는 장애 격리에 유리하고, 스레드는 같은 프로그램 내부의 작업을 병행할 때 활용합니다.”

예시: WPF와 별도 영상분석 프로그램의 TCP 연동은 프로세스 간 통신의 예입니다. WPF 내부의 UI 스레드와 영상 계산 작업 스레드는 멀티스레드의 예입니다.

꼬리질문: 프로세스 간 공유 메모리도 가능합니다. 스레드마다 스택은 별도이며, 치명적 오류는 프로세스 전체에 영향을 줄 수 있습니다. 여러 실행 흐름이 있다고 항상 여러 CPU 코어에서 동시에 실행되는 것은 아닙니다.

2. 비동기와 멀티스레드의 차이는?

“비동기는 작업 완료를 기다리는 동안 호출 흐름을 막지 않는 방식이고, 멀티스레드는 실행 스레드를 여러 개 사용하는 구조입니다. 네트워크 수신 같은 비동기 I/O는 기다리는 동안 전용 스레드를 점유할 필요가 없습니다. 반면 CPU 계산을 UI 밖에서 수행하려면 작업 스레드 활용을 고려합니다.”

async를 붙였다고 새 스레드가 생기거나 계산이 자동으로 빨라지는 것은 아닙니다.

3. async/await는 왜 쓰나요?

“비동기 작업의 완료를 기다리는 코드를 순차적인 형태로 작성하면서 호출 스레드를 막지 않기 위해 사용합니다. 완료되지 않은 작업을 await하면 제어를 호출자에게 돌려주고, 완료 후 이어서 실행합니다. I/O는 비동기 API를 사용하고 취소와 예외를 처리합니다.”

꼬리질문: WPF UI에서 .Result나 .Wait()로 동기 대기하면 화면이 멈추고, UI 컨텍스트로 돌아와야 하는 작업과 맞물리면 교착 상태도 생길 수 있습니다. async void는 주로 이벤트 핸들러에 한정합니다.

4. Task와 Thread의 차이는?

“Thread는 실제 실행 스레드를 다루는 객체이고, Task는 작업의 완료·결과·예외를 표현하는 추상화입니다. Task 하나가 스레드 하나를 뜻하지는 않습니다. Task.Run은 보통 스레드 풀에 작업을 맡기고, 비동기 I/O의 Task는 대기 중 전용 스레드가 없어도 됩니다.”

선택 이유: 일반적인 비동기 작업 조합에는 Task를 사용하고, 전용 스레드의 수명이나 특성을 직접 관리해야 하는 경우 Thread를 검토합니다.

5. WPF에서 UI가 멈추는 이유는?

“UI 스레드가 입력과 화면 갱신을 처리하는데, 긴 계산이나 동기 I/O로 점유되면 다른 UI 작업을 처리하지 못합니다. I/O에는 비동기 API를 사용하고, 무거운 계산은 필요할 때 작업 스레드로 옮깁니다. UI에 반영하는 작업 자체도 짧게 유지합니다.”

프로젝트 사례는 실제 사용한 방식으로 설명합니다. 모든 작업을 Task.Run으로 감쌌다고 답하지 않습니다.

6. Dispatcher는 왜 필요한가요?

“WPF UI 객체는 일반적으로 생성한 UI 스레드에서 접근해야 합니다. 백그라운드에서 받은 결과를 화면에 반영할 때 Dispatcher를 통해 UI 스레드에 작업을 전달합니다. 통신과 계산 전체를 Dispatcher 안에서 실행하면 다시 화면이 멈추므로 화면 갱신 부분만 전달합니다.”

꼬리질문: Invoke는 호출자가 완료를 기다리고, InvokeAsync는 비동기로 예약합니다. UI 컨텍스트에서 await한 뒤 복귀한 경우에는 이미 UI 스레드일 수 있습니다.

7. lock은 언제 쓰나요?

“여러 스레드가 공유 상태에 접근할 때, 확인과 변경을 하나의 임계 구역으로 보호해야 하는 경우 사용합니다. 같은 잠금 객체를 사용하는 코드끼리 한 번에 하나만 진입하게 합니다. 잠금 범위는 짧게 하고, 긴 장비 통신이나 외부 호출을 잠금 안에서 수행하지 않도록 설계합니다.”

꼬리질문: lock 안에서는 await할 수 없습니다. 비동기 상호 배제가 필요하면 SemaphoreSlim의 WaitAsync 등을 검토하고, 획득한 자원은 finally에서 해제합니다. 한쪽 코드만 잠그면 공유 상태가 안전해지는 것은 아닙니다.

8. 교착 상태란 무엇이고 어떻게 예방하나요?

“서로 필요한 자원을 점유한 채 상대가 풀어주기만 기다려 진행하지 못하는 상태입니다. 예를 들어 한 스레드는 A를 잠그고 B를 기다리는데, 다른 스레드는 B를 잠그고 A를 기다리는 경우입니다. 잠금 획득 순서를 통일하고 중첩 잠금을 줄이며, 잠금 중 외부 호출과 불필요한 동기 대기를 피합니다.”

타임아웃만 추가해서 끝내지 않고, 실패 시 이미 획득한 자원과 공유 상태를 어떻게 정리할지도 설명합니다.

2. TCP와 메시지 처리

9. TCP와 UDP의 차이는?

“TCP는 연결 기반의 바이트 스트림으로 전송 순서와 재전송을 관리합니다. UDP는 데이터그램 단위이며 전달·순서·중복 방지를 보장하지 않습니다. 어느 쪽을 쓸지는 장비 프로토콜과 지연·손실 요구사항에 따라 결정합니다.”

TCP가 데이터를 전달하는 것과 장비가 명령을 실행 완료하는 것은 다릅니다. 애플리케이션 수준의 응답·완료 확인과 타임아웃 정책이 별도로 필요합니다.

10. TCP에서 한 번 보낸 데이터가 한 번에 수신되나요?

“보장되지 않습니다. TCP는 메시지 경계를 유지하지 않아서 하나의 메시지가 나뉘어 오거나 여러 메시지가 함께 수신될 수 있습니다. 수신 버퍼에 누적한 뒤 길이 헤더나 구분자 등 프로토콜 규칙으로 완전한 메시지를 추출하고, 남은 데이터는 다음 수신 때 이어서 처리합니다.”

꼬리질문: 길이 값의 유효 범위와 최대 메시지 크기를 확인하고, 잘못된 프레임이나 불완전한 메시지의 처리 정책도 정합니다.

3. DB와 데이터 무결성

11. DB 트랜잭션은 왜 필요한가요?

“함께 성공해야 하는 여러 데이터 변경을 하나의 단위로 처리하기 위해 사용합니다. 예를 들어 검사 결과와 완료 상태가 같은 DB에 있다면 함께 커밋하거나 실패 시 롤백하여 일부만 반영되는 상태를 막습니다. 실제 적용 범위는 업무 규칙과 장애 시 복구 기준에 맞춰 정합니다.”

중요한 경계: DB 롤백은 이미 수행한 장비 분주나 외부 파일 저장을 되돌리지 못합니다. 실제 장비 상태 확인과 별도의 복구 절차가 필요합니다. SQLite와 JSON의 실제 역할은 구현 자료로 확인한 뒤 설명합니다.

12. 인덱스는 왜 쓰고 단점은 무엇인가요?

“조건 검색이나 조인·정렬에서 데이터를 찾는 비용을 줄이기 위해 사용합니다. 대신 저장 공간이 추가되고, 삽입·수정·삭제 때 인덱스도 유지해야 하므로 쓰기 비용이 증가합니다. 자주 사용하는 조회 조건과 데이터 분포를 보고 선정하고 실행 계획으로 효과를 확인합니다.”

검사 ID나 날짜 조건은 설명용 예시입니다. 실제 인덱스 구성은 확인 없이 단정하지 않습니다. 복합 인덱스는 컬럼 순서와 조회 조건이 중요합니다.

1. 왜 씨젠에 지원했습니까?

“제가 가장 오래 수행한 일이 IVD 자동화 장비 SW입니다. 씨젠 공고의 요구사항 분석, 모듈 연동, 통합시험과 현장지원이 QDST·dRAST에서 수행한 업무와 직접 연결됩니다. 최근 쌓은 IEC 62304 V&V와 사이버보안 경험까지 더해 의료 자동화 분야에서 장기적으로 기여하고 싶어 지원했습니다.”

2. 현재 회사에서 왜 이직하려 합니까?

“의료기기 SW 경험 중에서도 제가 가장 깊게 해 온 IVD 자동화에 다시 집중하려는 것이 첫 번째 이유입니다. 이제 가정도 생겨서, 탄탄한 회사에서 짧게 이동하기보다 한 분야에서 오래 책임지고 기여하려 합니다.”

전 직장 불만은 말하지 않는다. “생활 기반과 가까움”은 씨젠(송파)에 맞지 않아 쓰지 않는다.

“제노레이에서는 VENUS의 FDA 사이버보안 보완 대응에 집중 투입됐습니다. 그때 레이와트가 FDA를 본격적으로 시작한다는 제안을 받았고, 급하게 대응했던 내용을 처음부터 차근차근 검토하고 체계적으로 쌓을 수 있는 기회라고 판단해 옮겼습니다.”

“자동화 장비 UI만 만든 것이 아니라 검사 흐름, 장비 연동, 상태복구, 통합시험, 배포와 현장지원까지 경험했습니다. 여기에 의료기기 요구사항 추적, V&V와 사이버보안 검증 경험이 있어 기능 구현 단계부터 검증 증거와 운영 위험을 함께 볼 수 있습니다.”

6. 본인의 가장 큰 약점은 무엇입니까?

“경력이 Windows 의료기기 SW 중심이라 Web 제품 개발 경험은 부족합니다. 이를 숨기지 않고 ASP.NET Core Web API, 인증·권한, 실시간 상태 전달 구조를 학습하고 있습니다. 장비 상태관리·통신·DB·검증 경험을 기반으로 Web 실행환경의 차이를 빠르게 보완하겠습니다.”

12. 의료 자동화 시스템을 어떤 계층으로 나누겠습니까?

“장비 firmware, 통신 protocol, SW, 시약 lot와 assay 버전의 호환표를 관리하고 시작 시 조합을 확인합니다. 지원되지 않는 조합은 실행 전에 차단하고, 호환 범위를 변경할 때는 관련 요구사항과 통합시험을 함께 갱신합니다.”

16. 업데이트 중 실패하면 어떻게 복구합니까?

“설치 전 버전·DB schema·여유 공간과 무결성을 확인하고 기존 설정과 DB를 백업합니다. 애플리케이션과 DB migration의 성공을 각각 확인하며, 실패하면 호환 가능한 이전 버전으로 rollback합니다. 재시작 후 장비·DB 상태 확인까지 완료되어야 업데이트 성공으로 판단합니다.”

17. 장애 분석을 위해 어떤 로그를 남깁니까?

“검사 ID·검체 ID·장비·명령 ID를 연결하고 요청, ACK, 실제 완료, 상태 전환과 오류를 같은 시간 기준으로 기록합니다. 사용자 변경과 수동 복구는 audit log로 분리하고, 개인정보와 보안정보는 최소화하거나 보호합니다.”

18. 현장 장애 연락을 받으면 무엇부터 합니까?

“환자·검사 결과와 장비 안전 영향을 먼저 확인하고 추가 검사를 중단할지 판단합니다. 버전, 재현 순서, 로그와 장비 상태를 확보한 뒤 SW·통신·HW·운영 조건으로 가설을 나눕니다. 임시 조치와 근본 수정, 회귀시험과 배포 결과를 구분해 기록합니다.”

① 카메라·영상처리 — 5문항

1. 카메라 2대는 어떻게 사용했나요?

꼬리“MIL을 직접 다뤘나요?” → [확인] 카메라 설정 파일(DCF)·장치 번호·버퍼 구성 중 본인이 직접 한 범위만 말한다.
[확인] 지원서에는 “Template matching을 이용한 영상 획득”이라고 적었지만, 포트폴리오 검토 기록에는 “Template matching 알고리즘은 분석 엔진 쪽 코드, 본인은 호출·종료 코드 처리”로 되어 있음. 면접 전 어느 쪽이 맞는지 정리하고, 질문받으면 실제 범위로 답한다.

2. 초점은 어떻게 맞췄나요?

“QDST에서는 Projection으로 Focus mark를 찾고 Sobel 값으로 Z축 위치를 판단했습니다. dRAST에서는 Projection으로 초점 위치를 구하고 그 위치를 기준으로 항상 같은 곳으로 이동하게 했습니다.”

3. 영상 노이즈는 어떻게 처리했나요?

“OpenCV Thresholding으로 이진화하고 노이즈를 걸러냈습니다. Focus mark 불량을 따로 검출하는 프로그램도 만들어 키트 영상 상태를 확인했습니다.”

4. 고속 카메라 이미지 버퍼 관리 경험은?

“초당 수백 장을 받는 고속 라인 환경은 직접 해 보지 않았습니다. 제가 한 것은 슬롯·시간 단위로 촬영하고 저장·분석하는 구조였습니다. 고속 환경이라면 버퍼를 미리 잡아 재사용하고, 획득·처리·저장 스레드를 큐로 나눠 처리가 밀려도 획득이 멈추지 않게 하는 것부터 확인하겠습니다.”

뒤 문장은 실무 경험이 아니라 접근 방법이라고 구분해서 말한다.

C# ↔ C++ DLL 연동 기술 대응

공고의 핵심 우대사항입니다. 경험은 많지 않다고 먼저 말하고, 원리와 주의점을 정확히 설명해 신뢰를 얻습니다.

“C++ DLL 연동은 해 봤지만 많이 하지는 않았습니다. 그래도 연동할 때 문제가 되는 지점은 알고 있습니다. 데이터를 어떻게 넘기는지, 메모리를 누가 해제하는지, 콜백이 어느 스레드에서 오는지입니다.”
[확인] 실제로 연동했던 DLL(카메라 SDK, 모션 보드, 사내 C++ 모듈 등)을 하나 떠올려 두고, 그 사례로 첫 문장을 바꾼다. 아래 꼬리 답은 실무 성과가 아니라 알고 있는 원리로 말한다.
P/Invoke

C 함수 직접 호출

  • C++에서 extern "C"로 내보낸 함수를 DllImport(.NET 7+는 LibraryImport)로 호출
  • 함수 단위라 간단하고 빠름
  • C++ 클래스는 직접 못 씀 → C 함수로 감싸야 함
C++/CLI

중간 래퍼 DLL

  • 관리 코드와 네이티브 코드를 한 DLL에서 함께 씀
  • C++ 클래스·STL을 그대로 감싸 C#에 클래스로 노출
  • Windows·.NET 전용, 빌드·디버깅이 복잡
공통 위험

자주 터지는 곳

  • 호출 규약(cdecl/stdcall)·구조체 정렬 불일치
  • 메모리 해제 책임 혼동 → 누수·이중 해제
  • GC가 콜백 delegate를 수거 → 크래시
  • x86/x64 비트 불일치
// C++ (엔진 DLL)
extern "C" __declspec(dllexport)
int ProcessImage(const uint8_t* buf, int width, int height, int stride, Result* out);

// C# : 영상 버퍼를 복사 없이 포인터로 넘김
[DllImport("Engine.dll", CallingConvention = CallingConvention.Cdecl)]
static extern int ProcessImage(IntPtr buf, int width, int height, int stride, out Result result);

[StructLayout(LayoutKind.Sequential)]
struct Result { public int DefectCount; public float Score; }

unsafe
{
    fixed (byte* p = frame)          // 호출하는 동안만 GC가 못 옮기게 고정
    {
        int rc = ProcessImage((IntPtr)p, w, h, stride, out var r);
        if (rc != 0) throw new EngineException(rc);   // C++ 예외 대신 오류 코드
    }
}
예상 기술 질문과 꼬리 답 — 10문항

1. P/Invoke와 C++/CLI 중 무엇을 쓰나요?

“함수 몇 개를 부르는 정도면 P/Invoke가 단순합니다. C++ 엔진이 클래스 중심이고 주고받는 객체가 많으면 C++/CLI 래퍼가 편합니다. 다만 C++/CLI는 Windows 전용이고 빌드가 복잡해서, 경계를 얇은 C 함수로 정리할 수 있으면 P/Invoke를 먼저 고려합니다.”

2. 큰 영상 버퍼를 어떻게 넘기나요?

“복사하지 않고 포인터만 넘깁니다. C#에서 만든 배열이면 호출하는 동안만 fixed나 GCHandle.Alloc(Pinned)로 고정해 GC가 옮기지 못하게 합니다. 카메라 SDK가 준 네이티브 버퍼면 IntPtr 그대로 엔진에 넘깁니다.”

꼬리“계속 고정해 두면?” → GC 힙이 조각나 성능이 떨어집니다. 오래 쓰는 버퍼는 처음에 네이티브 메모리(NativeMemory.Alloc)나 POH(GC.AllocateArray(pinned: true))로 잡아 재사용합니다.

3. 마샬링 비용은 어떻게 줄이나요?

“int·float·고정 크기 구조체 같은 blittable 타입만 쓰면 변환 없이 그대로 넘어갑니다. string·bool·배열이 섞인 구조체는 변환 비용이 생기니, 반복 호출 경로에서는 피하고 포인터와 길이로 넘깁니다. 호출 횟수 자체도 줄여 한 프레임에 한 번 부르게 묶습니다.”

4. 메모리는 누가 해제하나요?

“할당한 쪽이 해제하는 게 원칙입니다. C++이 할당했으면 C++의 FreeResult() 같은 함수를 C#에서 불러 해제합니다. C#에서는 SafeHandle로 감싸 예외가 나도 해제되게 합니다. C++ new로 만든 걸 C#의 Marshal.FreeHGlobal로 지우면 안 됩니다.”

5. C++에서 C#으로 콜백은?

“delegate를 함수 포인터로 넘깁니다. 주의할 점이 두 가지입니다. delegate를 필드에 잡아 두지 않으면 GC가 수거해서 나중에 크래시가 납니다. 그리고 콜백은 C++ 스레드에서 오기 때문에 화면 갱신은 Dispatcher로 넘겨야 합니다.”

꼬리“콜백에서 오래 걸리는 일을 하면?” → 카메라 획득 스레드가 막혀 프레임이 빠집니다. 콜백에서는 버퍼만 큐에 넣고 바로 돌려줍니다.

6. C++ 예외가 C#으로 넘어오면?

“경계를 넘는 예외는 동작이 보장되지 않아서, C++ 쪽 export 함수에서 try-catch로 모두 잡고 오류 코드로 돌려줍니다. C#에서는 그 코드를 보고 예외로 바꿉니다.”

7. 고속 카메라에서 프레임 드롭은?

“획득·처리·저장을 다른 스레드로 나누고 사이에 큐를 둡니다. 버퍼는 미리 여러 개 잡아 돌려 쓰고(버퍼 풀), 처리가 밀리면 큐 길이로 바로 알 수 있게 합니다. 드롭이 나면 프레임 번호로 기록해서 어디서 밀렸는지 확인합니다.”

고속 카메라 실무 경험은 없다고 먼저 구분한다.

8. 처리된 영상을 WPF에 빠르게 표시하려면?

“WriteableBitmap을 한 번 만들고 Lock → 백버퍼에 복사 → AddDirtyRect → Unlock 순서로 갱신합니다. 매 프레임 새 비트맵을 만들지 않고, 표시 주기는 획득 주기보다 낮춰도 됩니다.”

9. 24시간 돌리면서 메모리 누수는 어떻게 찾나요?

“작업 관리자나 PerfMon으로 Private Bytes와 핸들 수를 장시간 기록합니다. 관리 힙은 그대로인데 프로세스 메모리만 늘면 네이티브 쪽 누수라서, 해제 짝이 맞는지와 SafeHandle 누락을 먼저 봅니다.”

10. 연동하다 크래시가 나면 어떻게 디버깅하나요?

“Visual Studio에서 Mixed 모드 디버깅을 켜면 C#과 C++ 스택을 같이 볼 수 있습니다. 현장에서는 덤프를 남겨 분석합니다. 흔한 원인은 호출 규약·구조체 정렬 불일치, x86/x64 불일치, 이미 해제된 메모리 접근, 수거된 콜백입니다.”

MVVM·Prism 질문 대응

dRAST 3.0 포트폴리오 2쪽에 Prism 구조를 적었으므로, 일반론이 아니라 포트폴리오 내용을 말로 풀어 답합니다.

“dRAST 3.0은 .NET 7과 WPF·Prism으로 만들었습니다. View는 입력과 표시만 하고, ViewModel이 화면 데이터와 서비스 호출을 맡습니다. 검사 상태는 Prism EventAggregator로 발행·구독해서 서비스가 화면을 직접 참조하지 않게 했습니다. 서비스는 Prism 컨테이너에 인터페이스로 등록해 생성자로 주입받고, 앱 시작 때 실장비와 Emulator 중 하나를 골라 연결합니다. 그래서 장비 없이도 같은 화면과 로직으로 검사 순서를 확인할 수 있었습니다.”
[확인] 2023년 Prism 리팩터링은 팀 작업이었음(기록상 로그인 SRS 백로그 담당). 본인이 직접 짠 부분과 팀 구조를 따른 부분을 한 문장으로 정리해 둔다. Region을 직접 구성했는지도 확인.
// 처리 순서: 화면 입력 → ViewModel → 서비스 호출 → 상태 이벤트 → 화면 갱신

// 1) 앱 시작: 실장비 / Emulator 중 하나를 같은 인터페이스로 등록
protected override void RegisterTypes(IContainerRegistry reg)
{
    if (settings.UseEmulator) reg.RegisterSingleton<IDeviceService, EmulatorDeviceService>();
    else                      reg.RegisterSingleton<IDeviceService, RealDeviceService>();
}

// 2) 서비스: 화면을 모름. 상태가 바뀌면 이벤트만 발행
public class TestEventStatusChanged : PubSubEvent<TestStatus> { }
_events.GetEvent<TestEventStatusChanged>().Publish(status);

// 3) ViewModel: 생성자로 주입받고, 이벤트를 UI 스레드에서 구독
public class TestListViewModel : BindableBase
{
    private string _status = "대기";
    public string Status { get => _status; set => SetProperty(ref _status, value); }

    public TestListViewModel(IDeviceService device, IEventAggregator events)
    {
        events.GetEvent<TestEventStatusChanged>()
              .Subscribe(s => Status = s.ToString(), ThreadOption.UIThread);
    }
}
위 코드는 구조 설명용 예시이며 실제 dRAST 소스가 아님. 클래스 이름을 실제 코드처럼 말하지 않는다.
꼬리 질문 — 7문항

1. 왜 EventAggregator를 썼나요?

“서비스가 ViewModel을 직접 부르면 서비스가 화면에 묶입니다. 상태 변경을 이벤트로 발행하면 화면이 몇 개든 필요한 곳만 구독하면 되고, 서비스는 화면이 있는지 몰라도 됩니다. 장비 스레드에서 발행돼도 ThreadOption.UIThread로 구독하면 화면 갱신이 UI 스레드에서 됩니다.”

2. EventAggregator의 단점은?

“이벤트가 많아지면 누가 발행하고 누가 받는지 추적하기 어렵습니다. 그래서 상태 전달처럼 여러 화면이 알아야 하는 것에만 쓰고, 한 화면 안의 동작은 Command와 바인딩으로 처리하는 게 낫다고 봅니다.”

3. DI를 쓴 이유는?

“가장 큰 이유는 Emulator입니다. 실장비와 Emulator가 같은 인터페이스를 구현하니, 등록만 바꾸면 나머지 코드는 그대로 장비 없이 돌아갑니다. 장비가 부족할 때 검사 순서를 PC에서 먼저 확인할 수 있었습니다.”

4. Prism의 Region은?

“메인 창의 영역에 이름을 붙여 두고, 그 자리에 들어갈 View를 이름으로 바꿔 끼우는 기능입니다. 메뉴로 검사·설정·로그 화면을 전환할 때 쓰고, ViewModel이 View 클래스를 직접 몰라도 화면을 바꿀 수 있습니다.”

[확인] dRAST에서 Region을 직접 구성했는지. 아니면 “구조는 알고 있다” 수준으로 말한다.

5. 리팩터링 전과 무엇이 달라졌나요?

“2022년 버전 화면은 코드 비하인드 방식이었습니다. 2023년에 팀 단위로 .NET 7·Prism 구조로 옮기면서 View, ViewModel, 서비스를 나눴고, 요구사항 번호에 맞춰 테스트를 작성했습니다.”

[확인] 리팩터링 동기(유지보수성, 테스트, FDA 문서화 등)를 기억으로 한 문장 정리.

6. CommunityToolkit.Mvvm과 차이는?

“툴킷은 [ObservableProperty], [RelayCommand] 같은 소스 생성기로 속성 알림과 Command를 줄여 주는 가벼운 라이브러리입니다. Prism은 여기에 Region 화면 전환, 모듈, 대화상자 서비스, DI 컨테이너까지 있는 프레임워크입니다. Prism으로 구조를 잡고 ViewModel은 툴킷으로 줄이는 조합도 가능합니다.”

7. 새 프로젝트라면 무엇을 쓰겠어요?

“기존 코드를 먼저 따르겠습니다. 새로 시작한다면 화면 수와 팀 규모로 정합니다. 설정 화면이 많은 검사장비면 Prism의 Region이 편합니다. 다만 Prism 9부터는 일정 규모 이상 회사에 상용 라이선스가 필요해서, 비용이 부담이면 툴킷에 간단한 화면 전환 서비스를 직접 만드는 쪽을 택하겠습니다.”

Prism 8.x까지는 MIT 무료. 9부터 Community(소규모 무료)·Commercial 라이선스. 비용 이야기로 길게 가지 않는다.
